## Agent Failure Atlas 2026: AI Agent Trajectory, Failure & Recovery Benchmark

> **This is a reproducible synthetic benchmark** designed for controlled
> experimentation on AI-agent failure, recovery, trajectory analysis and
> reliability. Trajectories and evidence are synthetically generated by a
> seeded, deterministic pipeline — not captured from production agent
> telemetry. It is built for research, benchmarking methodology, and
> education; results on this benchmark should not be interpreted as a
> direct measurement of real-world deployed-agent performance. See
> "Methodology" and "Limitations" below for exactly what that means.

### What is this?

A structured, relational benchmark of multi-step AI-agent execution
trajectories — each capable of containing **multiple, possibly cascading,
failures**, every one diagnosed against a documented taxonomy and paired
with its own recovery attempt(s). Not another prompt/response/pass-fail
dataset: a full `Task → Agent → Action → Tool → Observation → Decision →
Failure → Diagnosis → Recovery → Outcome → Evaluation` lifecycle, linked
end-to-end by consistent foreign keys.

### Why does it matter?

Most public agent datasets stop at whether an agent succeeded. That
doesn't tell you *how* it got there, *where* it went wrong, *whether the
failure caused another failure*, or *whether recovery actually worked*.
Studying agent reliability requires the structure this dataset provides,
not just a label.

### What's inside?

A synthetic, fully reproducible benchmark: **1,400 tasks**, **3,336
agent-run trajectories**, **43,477 trajectory steps**, **3,802 failure
events** (a run can have zero, one, or several — **31.6%** of runs have
2+), **4,334 recovery attempts** (a single failure can be retried with a
different strategy), and **11,737 evidence rows** backing a genuinely
computed grounding score. Generated by one seeded Python pipeline — see
Methodology below. Every foreign key resolves correctly: **107/107**
automated validation checks and **13/13** tests pass.

### Dataset structure

`tasks` → `agent_runs` → `trajectory_steps` → `failure_events` (self-
referencing via `parent_failure_id` for cascades) → `recovery_events`
(one-to-many: multiple attempts per failure), with `evaluations` and
`evidence` per run, and `agents` / `tools` / `taxonomy` as supporting
reference tables. Full schema and every field documented in
`docs/data_dictionary.md`.

### Failure taxonomy

30 failure types across 8 categories — `planning`, `tool_use`,
`retrieval`, `reasoning`, `state`, `verification`, `execution`, `output` —
each with a definition, example, a documented **numeric severity rubric**
(1=minor … 4=critical), and typical recoverability. Level-4
(`severity_level=4`) failures are never marked recoverable by taxonomy
design — verified: zero recovery attempts occur on any `severity_level=4`
failure in the data. See `docs/taxonomy.md`.

### Recovery analysis

9 documented recovery strategies (`retry`, `alternative_tool`,
`reformulate_query`, `verify_result`, `rollback`, `replan`,
`ask_for_clarification`, `use_additional_evidence`,
`change_execution_strategy`), each mapped to the failure categories they
apply to. Failures can receive **multiple recovery attempts** — later
attempts measurably succeed less often than the first, a real finding in
`notebooks/03_recovery_analysis.ipynb`, not an assumption.

### Failure cascades

A failure can be the documented cause of a later failure in the same run
(`is_cascading`, `parent_failure_id`), restricted to a hand-curated,
directionally-realistic edge list. **11.3%** of failure events are
cascades in this release — a real, analyzable slice of the data, covered
in both `notebooks/01_exploratory_analysis.ipynb` and
`notebooks/03_recovery_analysis.ipynb`.

### Evaluation

Per-run metrics — task success, constraint satisfaction, tool/trajectory
efficiency, a **genuinely computed** grounding score (mean of
`evidence.supports_claim`, not a sampled proxy), and a composite
reliability score — each with its exact computation documented in
`docs/methodology.md`. No metric is published without a stated formula.

### Research questions

Where do agents fail, and why? Does a failure cause other failures? Which
failures are recoverable, and which strategies actually work? Is trying
recovery again after a failed attempt worth it? Can failure be predicted
before task completion using only information available at the time
(`notebooks/02_predict_agent_failure.ipynb` — yes, with genuine,
leakage-free signal: ROC-AUC ≈ 0.84)?

### How to use it

```python
import pandas as pd
tasks = pd.read_csv("data/tasks.csv")
runs = pd.read_csv("data/agent_runs.csv")
steps = pd.read_csv("data/trajectory_steps.csv")
failures = pd.read_csv("data/failure_events.csv")
recoveries = pd.read_csv("data/recovery_events.csv")
evaluations = pd.read_csv("data/evaluations.csv")
evidence = pd.read_csv("data/evidence.csv")
```

Three notebooks are included and execute end-to-end against the published
files: exploratory analysis, a failure-prediction baseline, and a recovery
analysis.

### Limitations

This is a **synthetic simulation**, not real agent transcripts — see
`docs/methodology.md` for what that means for interpretation. Step content
is randomized-from-templates, not naturalistic free text. The
`evidence.csv` corpus is simulated, not real retrieved documents.
`MAX_FAILURES_PER_RUN=4` is an explicit safety cap. Full, unhedged
limitations list in the README and `docs/data_governance.md` — nothing is
hidden.
