# Methodology — Agent Failure Atlas 2026 (v2)

## What this dataset is

Agent Failure Atlas 2026 is a **structured simulation** of multi-step
AI-agent execution trajectories, not a corpus of real model transcripts.
Every table is produced by one deterministic, seeded Python pipeline
(`src/generation/generate_data.py`) that encodes a realistic causal
structure — which failure types occur at which decision categories, which
recovery strategies are applicable to which failure categories, how
failures can cascade into one another, how recovery outcome propagates to
final task status — without depending on live calls to any proprietary
model API.

This design choice is deliberate, not a shortcut:

1. **Reproducibility.** Anyone can regenerate the exact dataset from the
   published seed, with zero API cost and zero dependency on model
   availability or provider terms of service.
2. **Label correctness by construction.** Because failures, recoveries, and
   final status are generated by the same process (rather than annotated
   after the fact on noisy real transcripts), every foreign key and every
   status field is internally consistent — see `reports/final_quality_report.md`
   for the full validation results (107/107 checks passing at time of writing).
3. **No chain-of-thought exposure.** Real model transcripts would either
   need to omit private reasoning (losing information) or publish it
   (a governance risk this project explicitly avoids — see
   `docs/data_governance.md`). Simulation sidesteps this entirely.

The tradeoff, stated plainly: this dataset teaches the **structure and
statistics of agent failure/recovery lifecycles** — schema, taxonomy,
relational integrity, the shape of failure and recovery distributions — and
is a ready-made testbed for the notebooks' modeling questions. It does
**not** describe the true failure-rate distribution of any specific real
deployed agent system. See "Known Limitations" below and in the README.

## v2 upgrade — what changed from v1, and why

v1 (the initial MVP) allowed at most one diagnosed failure per trajectory,
sampled failure probability largely independently of observable features
(producing a near-chance ROC-AUC ~0.5 failure-prediction benchmark), used
fixed per-domain templates for step content, and sampled `grounding_score`
from a distribution conditioned on outcome rather than computing it. v2
addresses each of these directly:

| Weakness (v1 self-assessment) | v2 change |
|---|---|
| At most one failure per trajectory | `simulate_run` loops over candidate steps, injecting 0..`MAX_FAILURES_PER_RUN` (4) failures, each independently evaluated for recovery |
| Step content too templated | `render_tool_input`/`render_tool_output` randomize arguments, result sizes, and inject near-miss noise (timeouts, partial/malformed responses) independent of the failure label |
| `grounding_score` simulated, not evidence-based | New `evidence.csv` table with claim/support/contradict rows; `grounding_score` = mean(`supports_claim`) per run, a real computed aggregate |
| Failure prediction near-chance (ROC-AUC ~0.5) | `step_failure_probability` now depends on task difficulty, available tool count, trajectory depth, a retrieval-conflict flag, and agent capability tier — see below |
| Scale below target | Default generation scaled to 1,400 tasks / ~3,300 runs / ~43,000 steps (within the 3,000-5,000 trajectory / 30,000-100,000+ step target band) |

No schema table was removed or renamed; `evidence.csv` was added as a new
supporting table (see `docs/data_dictionary.md` for the full v1→v2 field
diff). Every change is reflected in the validator (`src/validation/validate.py`,
107 checks) and the test suite (`tests/test_dataset.py`, 13 tests).

## Generation pipeline

```
Task Generator          (make_tasks)                -> tasks.csv
Agent/Tool Catalogue     (build_reference_tables)    -> agents.csv, tools.csv, taxonomy.csv
Trajectory Generator     (gen_trajectory)            -> per-run step skeleton (randomized content)
Failure Injector         (simulate_run, looped)      -> failure_events.csv (0..N per run, cascading)
Recovery Generator       (simulate_run, per failure) -> recovery_events.csv (1..N attempts per failure)
Evidence Generator       (make_evidence_for_run)     -> evidence.csv
Evaluator                (evaluate_run)              -> evaluations.csv
Dataset Export           (generate)                  -> data/*.csv
Validator                (src/validation/validate.py)-> reports/final_quality_report.md
```

Each run in `agent_runs.csv` is generated in one pass:

1. **Task generation.** A task is sampled with a domain, difficulty, and
   topic; a description, constraints, success criteria, and an
   `available_tools` set (the domain's base toolset, plus a 4th tool on
   ~50% of tasks) are templated deterministically from these.
2. **Agent generation.** An agent configuration is sampled to execute the
   task, carrying a `capability_tier` (`high`/`medium`/`low`) — a labeled
   simulation parameter, not a real-model claim (see
   `docs/data_governance.md`).
3. **Tool simulation.** A trajectory skeleton is built: `planning` → a
   sequence of `retrieval`/`tool_selection`/`execution`/`correction` steps
   (length scales with difficulty: easy 4-8, medium 7-14, hard 12-22) →
   `verification` → `finalization`. Each tool-bearing step gets randomized
   arguments (`render_tool_input`) and a randomized, size-varying output
   (`render_tool_output`), with ~12% of tool-bearing steps additionally
   getting non-fatal noise (timeout, rate-limited, partial/malformed
   response, stale cache hit, schema mismatch) **independent of whether
   this run ends up with a diagnosed failure anywhere** — this is what
   makes the noise a realism feature rather than a leakage channel (see
   "Leakage avoidance" below).
4. **Trajectory generation + failure generation (looped).**
   `simulate_run` walks the candidate steps in order. At each one, a
   per-step failure probability is computed (see "Feature-driven failure
   probability" below) and a failure may be injected. The failure's
   category is constrained to those plausible for that step's decision
   category (e.g. a `retrieval` step can only fail with a `retrieval` or
   `tool_use` failure, never a `planning` failure), unless a cascade is
   active (see "Failure cascading" below). The loop continues — allowing
   further failures — until the run reaches its last candidate step, hits
   the 4-failure safety cap, or a critical failure goes unrecovered
   (which ends the run immediately).
5. **Failure diagnosis.** Each injected failure receives a `failure_type`,
   `failure_category`, text `severity`, and numeric `severity_level`
   (1-4, per the documented rubric in `docs/taxonomy.md`) inherited from
   the taxonomy — never assigned arbitrarily per-occurrence.
6. **Failure cascading.** After a failure is not (fully) resolved, there is
   a documented chance (55% for an unresolved non-critical failure that
   was attempted, 28% when the *last* recovery attempt itself fails, 10%
   even after a successful recovery) that the **next** injected failure in
   this run is drawn from that failure type's documented cascade targets
   (`FAILURE_CASCADES` in `src/generation/taxonomy.py`) rather than sampled
   independently — producing `is_cascading=True` and a populated
   `parent_failure_id`. Cascade edges are hand-curated to be directionally
   realistic (e.g. `retrieval_miss` can cause `incorrect_inference`, not
   vice versa).
7. **Recovery generation.** If the failure type is typically recoverable,
   recovery is attempted with 85% probability. Non-critical failures may
   receive **up to 2 attempts**: each attempt draws a strategy from that
   failure category's applicable-strategies list, with success probability
   equal to the strategy's base rate (halved in effect for critical
   failures, and reduced by a further 15% per repeated attempt on the same
   failure — repeated recovery is not free). Each attempt inserts 1-3
   recovery steps into the trajectory and produces its own
   `recovery_events` row (`recovery_attempt_number` 1, 2, …).
8. **Evidence generation.** A small set of claim/evidence rows (2-5 per
   run) is generated, with `supports_claim` probability conditioned on the
   run's actual `final_status` and whether a retrieval-conflict flag was
   set for this run — `grounding_score` is then the real mean of
   `supports_claim` across these rows, not a separately-sampled proxy.
9. **Final status derivation.** `success` (no failures, or every failure
   ultimately recovered), `partial_success` (at least one non-critical
   failure was never successfully recovered), `failed` (a critical failure
   went unrecovered — this ends the run immediately, so a `failed` run's
   `failure_count` reflects only the failures that occurred up to and
   including the fatal one).
10. **Cost aggregation.** Latency and token counts are sampled per step and
    summed; every recovery attempt's latency/token cost is added on top.
11. **Validation.** `src/validation/validate.py` runs 107 checks —
    referential integrity, uniqueness, nulls, enums, sequencing, numeric
    bounds, multi-failure ordering, cascade consistency, recovery-attempt
    ordering, and label-leakage detection — and writes
    `reports/final_quality_report.md`.

## Feature-driven failure probability

This is the mechanism behind the v2 failure-prediction upgrade
(`notebooks/02_predict_agent_failure.ipynb`). For each candidate step, the
failure probability is:

```
p = base_prob
  + 0.045 * difficulty_ordinal          # 0 (easy), 1 (medium), 2 (hard)
  + 0.010 * max(available_tool_count - 3, 0)
  + 0.003 * min(steps_so_far, 20)
  + 0.06  * has_conflict_flag           # task-level retrieval-conflict flag
  + {high: -0.01, medium: 0.0, low: +0.025}[capability_tier]
  + 0.02  * (prior_failure_count > 0)   # a run already in trouble trips slightly more
```

clipped to `[0, 0.85]`. Effects are **additive nudges, not multiplicative
factors** — this was a deliberate correction during development: an early
multiplicative version compounded across a 10-20 step trajectory into a
93% failure rate, which is not a realistic distribution and would have
made every run look the same. The additive form keeps each factor's
individual contribution modest while still producing a measurable,
learnable difference in failure rate across difficulty/tool-count/
capability-tier strata (verified: `easy` tasks fail at ~15%, `hard` tasks
at ~73%, in the published release — see `notebooks/02_predict_agent_failure.ipynb`).

`has_conflict_flag` is set once per run (18% probability) and represents
"were this run's retrieved sources conflicting" — it also feeds
`evidence.csv` generation, but is **not** exposed as a notebook feature,
since a real early-warning system could not cleanly observe it before a
failure occurs (see that notebook's Limitations).

## Leakage avoidance

Two safeguards keep this dataset (and its own failure-prediction notebook)
honest:

1. **Text leakage.** `trajectory_steps.observation` never contains
   failure-indicating language (`"Failure detected"` etc.) while
   `step_status='ok'` — validated automatically
   (`src/validation/validate.py`, `tests/test_dataset.py::test_no_label_leakage_in_pre_failure_steps`).
   The near-miss noise injected into ~12% of tool-bearing steps (timeouts,
   partial responses, etc.) appears on **both** failing and non-failing
   runs — verified directly (`test_no_label_leakage_in_pre_failure_steps`'s
   companion validator check confirms noisy text occurs in runs with and
   without a diagnosed failure), so it cannot be used as a proxy label.
2. **Feature leakage.** `agent_runs.tool_call_count`, `latency_ms`, and
   `total_tokens` are **whole-run aggregates that include recovery steps**
   — a run with 4 failures has roughly 4x the tool calls of a clean run,
   by construction, so using these as failure-prediction features would
   leak the label almost perfectly. `notebooks/02_predict_agent_failure.ipynb`
   avoids this entirely by computing trajectory-shape features only from
   the **prefix of steps strictly before a run's first diagnosed failure**
   (capped at 6 steps) — exactly the information available to a real-time
   monitor before any failure is known to have occurred.

## Evaluation metrics — exact computation

Every metric in `evaluations.csv` is computed as follows (also see
`docs/data_dictionary.md`):

- **task_success**: `final_status in {success, partial_success}`.
- **constraint_satisfaction**: `1.0` if `success`, `0.5` if
  `partial_success`, `0.0` if `failed`. A coarse proxy — this release does
  not parse the free-text `constraints` field to check satisfaction
  per-constraint (see Limitations).
- **critical_failure_count**: count of this run's failures with
  `is_critical == True` (severity_level 3 or 4).
- **cascading_failure_count**: count of this run's failures with
  `is_cascading == True`.
- **recovery_success_rate**: `len(recovered failure_ids) / failure_count`
  for this run; `null` when `failure_count == 0` (never fabricated as
  `0` or `1`). Replaces v1's single boolean `recovery_success`, which
  could not represent a run with multiple failures and mixed outcomes.
- **tool_efficiency**: `min(1.0, expected_tool_count / actual_tool_calls)`,
  where `expected_tool_count = max(2, trajectory_length // 3)` — a simple
  proxy for "did the run use roughly as many tool calls as its length would
  suggest," not a ground-truth-optimal tool count (no such ground truth is
  computed in this release).
- **trajectory_efficiency**: `min(1.0, reference_length / actual_length)`,
  with `reference_length` = 8 steps for `easy` tasks and 14 for
  `medium`/`hard` — again a simple proxy, not a solved-optimal path length.
- **grounding_score**: **v2 — genuinely computed**, not sampled. Equal to
  `mean(evidence.supports_claim)` across this run's `evidence.csv` rows.
  Evidence rows are themselves generated with a support probability
  conditioned on the run's actual outcome and conflict flag (see
  "Generation pipeline" step 8) — so the score is a real aggregate of
  explicit claim/support data, not a distribution sampled independently of
  any underlying evidence object. It is still a **simulated** evidence
  corpus (no real retrieved documents exist in this release), so it should
  be read as "grounding score under this dataset's simulated evidence
  model," not a measurement against real-world source text.
- **final_answer_score**: `1.0` / `0.5` / `0.0` for success / partial /
  failed — mirrors constraint_satisfaction by construction in this release.
- **reliability_score**: weighted composite,
  `0.5*task_success + 0.2*(1 - has_critical_failure) + 0.2*(recovery_success_rate or 1 if no failure) + 0.1*tool_efficiency`,
  clipped to `[0, 1]`.

No metric that could not be reliably computed from the generated trajectory
was included (e.g. we do not publish a fabricated "hallucination score"
that would require real retrieved content to check against).

## Known limitations of the methodology

- **Templated-with-randomization, not model-generated, step content.**
  `tool_input`/`tool_output`/`observation` text is generated from
  randomized templates (varied arguments, result sizes, noise), not
  outputs of an actual tool or model call. v2 is materially more varied
  than v1 but is still not naturalistic free text — a human or LLM judge
  could likely still distinguish it from a real transcript on close
  reading.
- **`ground_truth` in tasks.csv is a reference key, not a resolvable
  answer artifact**, since no external corpus is attached in this release.
- **The evidence corpus is simulated, not real retrieved content** — see
  the `grounding_score` note above. A future version could attach a real,
  small fixed document corpus and compute genuine text-based support
  detection.
- **Failure cascades are hand-curated edges** (`FAILURE_CASCADES`), not
  learned or derived from a causal model — they encode plausible
  directional relationships (e.g. retrieval problems can cause downstream
  reasoning problems) but are a modeling choice, documented as such.
- **`MAX_FAILURES_PER_RUN=4` is a safety cap**, not a claim about a
  realistic maximum — it exists to bound worst-case generation and dataset
  size. In the published release it functions as the natural tail of a
  tapering distribution (0-failure runs are most common, 4-failure runs
  least common among the failure counts, at roughly 13% of *failing*
  runs / 8% of *all* runs) rather than a hard wall most runs hit — but it
  is still an explicit ceiling, not an emergent property, and should be
  read as such.
