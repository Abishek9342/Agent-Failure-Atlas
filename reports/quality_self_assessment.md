## One real finding from this audit pass, and how it was fixed

Auditing the recovery data against the README's own claims surfaced a
genuine documentation imprecision (not a data bug): the README and Kaggle
description said "zero recovery attempts occur on any critical failure,"
but **61 `is_critical=True` failures did have a recovery attempt**. On
inspection, this is correct behavior, not a bug — `is_critical` (the
boolean) covers **both** `severity_level` 3 ("major," documented
recoverable-but-harder) and 4 ("critical," documented unrecoverable), and
only level 4 is actually guaranteed zero attempts (verified: 0 recovery
attempts on any `severity_level=4` failure, exactly as designed). The
prose conflated the boolean flag with the taxonomy's narrower "critical"
severity band. Fixed in `README.md` and `docs/kaggle_description.md` to
say `severity_level=4` explicitly rather than the ambiguous word
"critical" alone. This is exactly the kind of issue a "verify, don't
trust prior claims" audit is supposed to catch — recorded here rather
than silently corrected.

Also found and fixed during this pass: the required synthetic-data
disclaimer sentence (spec-mandated verbatim text) was written into the
original spec but never actually landed in any doc — added to
`docs/data_governance.md` and `README.md`. The explicit synthetic-vs-real
predictive-performance warning was similarly missing from Notebook 2 —
added, and the notebook re-executed to confirm it still runs clean.
`requirements.txt` listed `scipy`, `seaborn`, `pydantic`, `jsonschema`,
`tqdm`, and `python-dotenv` — none of which are imported anywhere in the
actual codebase (verified by grepping every `.py` file) — trimmed to the
7 packages genuinely used, per the spec's own "only retain packages that
are genuinely required" instruction. Stale `__pycache__`/`.pytest_cache`
directories (generated by running the test suite, not part of the
intended package) were also found and removed.

## Research findings (main, re-verified)

1. 58.0% of runs experience >=1 failure; 31.6% of *all* runs experience
   multiple failures.
2. 11.3% of failure events are documented cascades, concentrated in
   state/tool_use → execution/output chains.
3. `severity_level=4` failures never receive a recovery attempt — 0 cases
   confirmed directly against `recovery_events.csv`, matching taxonomy
   design intent. (`is_critical`, the broader flag covering levels 3-4,
   *can* and does receive attempts — 61 level-3 cases in this release,
   correctly so per the taxonomy's recoverability rules.)
4. Repeated recovery attempts on the same failure succeed less often than
   the first attempt (61.7% vs 52.4%).
5. Failure prediction from pre-completion features reaches ROC-AUC ≈ 0.84
   without any leakage.
