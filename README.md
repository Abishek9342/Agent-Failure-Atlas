# Agent Failure Atlas 2026: AI Agent Trajectory, Failure & Recovery Benchmark

**Multi-Step AI Agent Trajectories for Failure, Recovery & Tool-Use Analysis**

> Agents fail in different ways. Agent Failure Atlas 2026 makes those
> failures measurable.

*"Agent Failure Atlas 2026" is the brand name for this dataset and the
series it may grow into; the extended title above exists for search
keyword coverage.*

> **This is a reproducible synthetic benchmark** designed for controlled
> experimentation on AI-agent failure, recovery, trajectory analysis and
> reliability. Trajectories and evidence are synthetically generated by a
> seeded, deterministic pipeline — not captured from production agent
> telemetry — so results here should not be interpreted as a direct
> measurement of real-world deployed-agent performance. See
> [Limitations](#limitations) for exactly what that means.

## What it is

A structured, relational benchmark of multi-step AI-agent trajectories —
each capable of containing **multiple, possibly cascading, failures**,
each with its own recovery attempt(s) — for failure diagnosis, recovery
analysis, tool-use evaluation, and agent reliability research.

## Why this dataset exists

AI agents are increasingly capable of performing multi-step tasks, but most
public agent datasets stop at prompts, model responses, and a pass/fail
label. That's not enough to study failure *mechanics*. This dataset instead
captures the full structured lifecycle of an agent execution:

```
Task -> Agent -> Action -> Tool -> Observation -> Decision
     -> Failure -> Diagnosis -> Recovery -> Final Outcome -> Evaluation
```

with failures allowed to **cascade** into one another within a single run.

The central research question:

> **How do AI agents fail, why do they fail, and can they recover?**

## Who should use it

Researchers studying agent reliability and failure taxonomy; ML/AI
engineers building or evaluating agent systems; students and final-year
project teams looking for a relational dataset with a real classification
task attached; benchmark researchers comparing evaluation methodologies.

## Key questions

- Where did the agent fail, and why?
- Was the failure recoverable — and did recovery actually work?
- How do failures cascade into one another within a trajectory?
- Can failure be predicted before task completion? (Notebook 2 — v2 now
  has genuine, non-leaking predictive signal, ROC-AUC ≈ 0.84.)
- Which recovery strategies work, and what does recovery cost?

## Dataset contents

Ten tables: the core relational chain, plus supporting reference tables.

```
tasks ──< agent_runs ──< trajectory_steps
               │               │
               │               └──< failure_events ──< recovery_events
               │                        │  (parent_failure_id: cascades)
               ├──< evaluations
               └──< evidence

agents, tools, taxonomy — supporting reference tables
```

| Table | Rows | Description |
|---|---:|---|
| `tasks.csv` | 1,400 | One row per unique task (domain, difficulty, constraints, available tools, ground truth, success criteria). |
| `agents.csv` | 10 | One row per agent configuration (model, provider, framework, capability tier, temperature, tool policy). |
| `tools.csv` | 10 | Tool catalogue (category, schema, risk level). |
| `taxonomy.csv` | 30 | Machine-readable failure taxonomy (8 categories × their sub-types), with a documented severity rubric and cascade edges. |
| `agent_runs.csv` | 3,336 | One row per complete agent execution on a task. |
| `trajectory_steps.csv` | 43,477 | One row per observable execution step — reconstructs the full trajectory. |
| `failure_events.csv` | 3,802 | One row per diagnosed failure — **a run can have zero, one, or several**, and failures can cascade (`parent_failure_id`). |
| `recovery_events.csv` | 4,334 | One row per recovery **attempt** — a failure can have more than one attempt. |
| `evaluations.csv` | 3,336 | One row per run: success, efficiency, grounding, and reliability metrics. |
| `evidence.csv` | 11,737 | One row per claim/evidence relationship — the basis for a genuinely computed `grounding_score`. |

Every field is documented in [`docs/data_dictionary.md`](docs/data_dictionary.md).
Every foreign key resolves correctly — see `reports/final_quality_report.md`
(107/107 automated checks passing; 13/13 tests passing).

## Schema

```
tasks.task_id              <── agent_runs.task_id
agents.agent_id             <── agent_runs.agent_id

agent_runs.run_id           <── evaluations.run_id   (1:1)
agent_runs.run_id           <── evidence.run_id
tools.tool_name              <── trajectory_steps.tool_name (nullable)
taxonomy.level_2             <── failure_events.failure_type
```

## Dataset statistics

(Measured directly from the published files — not placeholders.)

- **1,400** tasks across **13 domains** — no domain exceeds **8.7%** of tasks.
- **3,336** agent-run trajectories, across **10** agent configurations
  spanning several simulated model families and 3 capability tiers.
- **43,477** trajectory steps.
- **3,802** failure events, **4,334** recovery attempts, **11,737**
  evidence rows.
- **42.0%** clean success (no failure at all); **58.0%** of runs
  experienced ≥1 failure; **31.6%** of *all* runs experienced **≥2
  failures** (multi-failure trajectories); **11.3%** of failure events are
  documented cascades (`is_cascading=True`).
- Of failures, recovery was attempted **75.4%** of the time, succeeding
  **60.3%** per attempt — overall task success (including recovered runs)
  is **60.2%**.
- This is the dataset's *real, measured* distribution — not forced into a
  preset target band. Full breakdown (severity, domain, model): `reports/final_quality_report.md`.

## Failure taxonomy

Eight top-level categories — `planning`, `tool_use`, `retrieval`,
`reasoning`, `state`, `verification`, `execution`, `output` — each with
3-5 specific failure types (30 total), every one with a definition,
concrete example, a documented numeric severity rubric (1=minor …
4=critical), and typical recoverability. Level-4 (`severity_level=4`,
the taxonomy's "critical" band — distinct from the broader `is_critical`
flag, which also covers level 3) failures are never marked recoverable,
by taxonomy design — verified directly in the data: zero recovery
attempts occur on any `severity_level=4` failure. `is_critical` (levels 3
**and** 4) failures *can* still receive recovery attempts — 61 level-3
failures did in this release, since level 3 ("major") is documented as
recoverable-but-harder, not unrecoverable. Full taxonomy, including
cascade edges: [`docs/taxonomy.md`](docs/taxonomy.md).

## Recovery taxonomy

Nine recovery strategies — `retry`, `alternative_tool`,
`reformulate_query`, `verify_result`, `rollback`, `replan`,
`ask_for_clarification`, `use_additional_evidence`,
`change_execution_strategy` — each mapped to the failure categories it's
plausible for. A single failure can receive **multiple attempts** with
different strategies; later attempts succeed less often (a measured
effect, not just a documented assumption — see
`notebooks/03_recovery_analysis.ipynb`). Full definitions:
[`docs/taxonomy.md`](docs/taxonomy.md).

## Failure cascades

A failure can be the documented cause of a later failure in the same run
(`is_cascading=True`, linked via `parent_failure_id`, restricted to a
hand-curated, directionally-realistic edge list — e.g. a retrieval problem
can cause a downstream reasoning problem, never the reverse). This is a
first-class analytical feature, not an afterthought — see
`notebooks/01_exploratory_analysis.ipynb` §4 and
`notebooks/03_recovery_analysis.ipynb` for cascade frequency, common
chains, and whether cascading failures recover differently than
independent ones.

## Evidence

`evidence.csv` (11,737 rows) holds one claim/source relationship per row
— `source_type`, `claim`, `relevance`, `supports_claim`,
`contradicts_claim` — generated alongside each run. It exists so
groundedness can be *computed*, not guessed: see Evaluation below.

## Evaluation

Every metric in `evaluations.csv` — `task_success`,
`constraint_satisfaction`, `critical_failure_count`,
`cascading_failure_count`, `recovery_success_rate`, `tool_efficiency`,
`trajectory_efficiency`, `grounding_score`, `final_answer_score`,
`reliability_score` — has its exact computation documented in
[`docs/methodology.md`](docs/methodology.md). `grounding_score` is a
genuinely computed aggregate over the `evidence.csv` table (mean of
`supports_claim`), not a value sampled independently of any underlying
evidence object.

## Example: a multi-failure, cascading trajectory

Task `task_00004` (planning, hard): *"Produce a 4-step plan to accomplish
hiring pipeline metrics respecting the stated constraints."* Run
`run_000009` (agent `agent_10`) — **3 failures, one a cascade, one with
two recovery attempts**:

| # | failure_type | category | severity | cascade | recovery attempts | outcome |
|---|---|---|---|---|---|---|
| 1 | `repeated_tool_call` | tool_use | 1 (minor) | independent | 1 attempt (`retry`) | ✅ recovered |
| 2 | `memory_failure` | state | 1 (minor) | independent | 1 attempt (`replan`) | ❌ not recovered |
| 3 | `constraint_violation` | reasoning | 3 (major) | **cascaded from failure 2** | 2 attempts (`verify_result` failed, then `use_additional_evidence` succeeded) | ✅ recovered on 2nd attempt |

`agent_runs.final_status` for this run is **`partial_success`** — even
though failure 3 was eventually recovered, failure 2 (`memory_failure`)
never was, so the run does not count as a clean success. This is exactly
the kind of nuance a flat pass/fail label would hide, and exactly what the
relational schema is built to expose.

```python
failures = pd.read_csv("data/failure_events.csv")
recoveries = pd.read_csv("data/recovery_events.csv")

# reconstruct one full trajectory, including its failure cascade
run_id = "run_000009"
print(steps[steps.run_id == run_id].sort_values("sequence_number"))

```

## Notebooks

1. **`01_exploratory_analysis.ipynb`** — "How AI Agents Fail." Schema
   walk, task/model/tool distribution, failures-per-trajectory, cascade
   analysis, severity, tool/domain/model breakdowns, latency/cost, recovery
   rate. Ends with 5 genuine findings.
2. **`02_predict_agent_failure.ipynb`** — "Can We Predict Agent Failure?"
   Logistic Regression / Random Forest / Gradient Boosting on strictly
   pre-failure features (task/agent metadata + a pre-failure trajectory
   prefix), with an explicit majority-class baseline and a leakage
   explanation. Reaches ROC-AUC ≈ 0.84 — a genuine improvement over v1's
   near-chance result, achieved by making failure probability legitimately
   feature-dependent in the generator, not by loosening the leakage rules.
3. **`03_recovery_analysis.ipynb`** — "Can AI Agents Recover From
   Failure?" failure_type → recovery_strategy → recovery_success, severity,
   repeated attempts, cascades, and cost.

## Limitations

> **The benchmark uses synthetic evidence and synthetic trajectories; it
> is intended for controlled research and educational experimentation
> rather than as a substitute for real production agent logs.**

Read in full: [`docs/methodology.md`](docs/methodology.md) and
[`docs/data_governance.md`](docs/data_governance.md). In short:

- **This is a synthetic simulation, not real model transcripts.** Task
  descriptions, trajectory content, and failure/recovery events are
  generated by a documented, seeded pipeline — not sampled from live model
  API calls. This buys full reproducibility and internally-consistent
  labels at the cost of not describing any real deployed agent's actual
  behavior. See `docs/methodology.md` for the full rationale.
- **Step content is randomized-from-templates**, not naturalistic free
  text or real model/tool output.
- **`MAX_FAILURES_PER_RUN=4` is an explicit safety cap**, not an emergent
  property — see `docs/methodology.md`.
- **Failure cascade edges are hand-curated**, not learned from a causal
  model.
- **`evidence.csv` is a simulated evidence corpus**, not real retrieved
  documents — `grounding_score` is genuinely *computed* from it (a real
  v2 improvement over v1's sampled proxy), but should be read as
  "groundedness under this dataset's simulated evidence model," not a
  measurement against real-world source text.
- **`agents.capability_tier` is a labeled simulation parameter**, not a
  real capability ranking of the named model families.

## How this differs from existing agent-evaluation resources

Full competitor research: [`research/competitor_analysis.md`](research/competitor_analysis.md)
(2026-08-27). The agent-evaluation/failure space is active and crowded at
the research-paper level (AgentBench, WebArena, GAIA, ToolBench, TRAIL,
AgentRx, ATBench, ToolFailBench, AgentErrorBench, and others) — but nearly
every project found is either a single flat table/raw-trace corpus, sourced
from real model transcripts with a narrow one- or two-domain scope, or a
research protocol rather than a downloadable structured dataset. The one
direct Kaggle competitor found
(`sunil123kumar/ai-agent-failure-benchmark-dataset`, ~1,500 samples) appears
single-table; its full schema could not be verified.

This dataset's differentiation is **structural, not a novelty claim**: a
full relational chain (`tasks → agent_runs → trajectory_steps →
failure_events → recovery_events`, plus `evaluations`/`evidence`/`agents`/`tools`)
with **multi-failure, cascading trajectories** and a `recovery_events`
table as a first-class citizen supporting **repeated recovery attempts**,
a taxonomy generated from one source-of-truth script so documentation
can't drift from data, and candid documentation of its own limitations. No
"first ever" claim is made.

## Versioning

**v2 (this release)** — 1,400 tasks, 3,336 trajectories, 43,477 steps.
Multi-failure and cascading trajectories, feature-driven (non-leaking)
failure probability giving genuine ROC-AUC ≈ 0.84 predictive signal,
randomized trajectory content, repeated recovery attempts, and a real
evidence-based `grounding_score`.

**v1** — 900 tasks, 2,202 trajectories, 25,964 steps. At most one failure
per trajectory, near-chance (ROC-AUC ~0.5) failure prediction, templated
step content, sampled (not computed) `grounding_score`. Superseded by v2;
kept only as the documented starting point in `docs/methodology.md`'s "v2
upgrade" changelog.

Planned for a future version (not implied to exist yet): a real, fixed
document corpus backing `evidence.csv` instead of a simulated one; a
learned (not hand-curated) cascade model; scale further toward the upper
end of the 3,000-5,000 trajectory target if quality permits.
